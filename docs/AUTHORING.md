# Writing units and hosting a marketplace

## A unit

One folder. The only required file is `unit.toml`.

```
units/reopen/
  unit.toml        what this is, what it needs, which keys it claims
  hypr/*.lua       linked into ~/.config/hypr/modules.d/
  bin/*            linked into ~/.local/bin/
  plugin/          linked into ~/.config/omarchy/plugins/<id>/   (kind = plugin)
  apply.sh         run on add                                    (kind = setting)
  revert.sh        run on remove                                 (kind = setting)
  README.md        optional, for humans
```

```toml
name     = "reopen"
summary  = "SUPER+Z reopens the window you closed last"
version  = "0.1.0"
category = "Productivity"
tags     = ["hyprland", "windows"]
author   = "pehcastro"
kind     = "hypr"
needs    = ["hyprctl", "socat", "jq"]
keys     = ["SUPER+Z"]
```

`unit.toml` is a strict subset of TOML: `key = "value"` and `key = ["a", "b"]`,
one per line, no tables, no multi-line values. That is deliberate, so `bo` can
read it with `sed` and no dependency.

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | must equal the folder name |
| `summary` | yes | one line, shown in every listing |
| `version` | yes | bump it when you change the unit |
| `kind` | yes | `plugin`, `hypr`, or `setting` |
| `category` | no | one word, for grouping |
| `tags` | no | searchable |
| `author` | no | you |
| `id` | plugins | the Omarchy plugin id, matching `plugin/manifest.json` |
| `needs` | no | commands that must exist; `bo doctor` checks them |
| `keys` | no | what you bind; `bo status` flags two units claiming one key |

### kind

`kind` only decides the extra step. **Any unit may carry `hypr/` and `bin/`,
whatever its kind**, because a bar widget that also wants a keybinding is
normal.

- `plugin`: `plugin/` is symlinked into `~/.config/omarchy/plugins/<id>/`, then
  `bo` rescans and enables it. `plugin/manifest.json` is an ordinary Omarchy
  plugin manifest; `bo validate` runs `omarchy plugin validate` on it.
- `hypr`: nothing extra. The `hypr/*.lua` files do the work.
- `setting`: `apply.sh` runs on add, `revert.sh` on remove. Use this for state
  Omarchy owns, such as a toggle, rather than reimplementing it.

### Two things that will bite you

**Symlinks inside a plugin folder fail Omarchy's validator.** A symlinked plugin
*directory* is fine, because the scanner uses `find -L`. That is why `bo` links
the whole `plugin/` folder and never file by file.

**Hyprland's `require_all` will not see your Lua.** It runs `find -type f`,
which does not match a symlink. `bo` writes its own loader that uses `find -L`
and `dofile`, so this is handled for you: just put `.lua` files in `hypr/` and
write them as you would any Omarchy Lua config. `o.bind`, `hl.config`,
`hl.workspace_rule` and friends are all in scope.

**Do not use dots in a Lua filename.** The loader uses `dofile`, so it does not
matter here, but `require` turns each dot into a path separator, and someone
will eventually copy your file into a config that uses `require`.

## A marketplace

A git repo with three things at its root:

```
marketplace.json     who you are
registry.json        generated, committed
units/               the units
tools/build-registry optional, if you want the generator
```

```json
{
  "name": "acme",
  "title": "Acme units",
  "description": "What this collection is for",
  "homepage": "https://github.com/acme/omarchy-units",
  "maintainer": "acme"
}
```

`name` is what users type: `bo add acme/thing`. Pick something short and
unlikely to collide.

### registry.json

Generated by `tools/build-registry`, committed to the repo. It holds everything
from every `unit.toml` plus three things only git knows:

```json
{
  "schema": 1,
  "name": "acme",
  "generated_at_commit": "8c0f1a...",
  "units": {
    "thing": {
      "name": "thing",
      "summary": "...",
      "version": "1.2.0",
      "kind": "hypr",
      "category": "Other",
      "tags": ["test"],
      "author": "acme",
      "needs": [],
      "keys": ["SUPER+F2"],
      "pluginId": "",
      "path": "units/thing",
      "files": 3,
      "hash": "225073f34b48...",
      "commit": "d5d89fe4451b...",
      "updated": "2026-08-18T17:21:52-03:00",
      "author_last": "Acme Person"
    }
  }
}
```

`hash` is content, not git: it is the sha256 of every tracked file in the unit.
An unrelated commit does not change it, so `bo update` can tell a real change
from a reshuffle, and `bo outdated` can compare what a user has against what you
published without re-hashing their tree.

Regenerate and commit it with every change:

```bash
./tools/build-registry
git add registry.json && git commit
```

If you forget, `bo update` will show the unit as unchanged and users will not
get it. A pre-commit hook is worth the five lines.

### Publishing

Push it. That is the whole distribution mechanism.

```bash
bo market add https://github.com/acme/omarchy-units
```

`bo` clones it, reads `registry.json` for the name, and refuses a repo that has
no registry at its root. `bo market update` fast-forwards; it will not merge
over local commits.

### Versioning

Bump `version` in `unit.toml` when you change a unit. `bo update` prints
`0.1.0 -> 0.2.0` when you do and `(content changed, version did not)` when you
do not, which is a nudge, not an error.

## Testing a unit before you publish

```bash
bo market add /path/to/your/repo    # a local path works
bo info your/unit
bo add your/unit
bo status                           # did you take a key someone else has?
bo doctor                           # is everything you declared installed?
bo remove your/unit                 # does removal leave anything behind?
```

The last one matters most. After `bo remove`, check `~/.config/hypr/modules.d`,
`~/.local/bin` and `~/.config/omarchy/plugins` for anything of yours still
there. `bo` only unlinks symlinks that point into a marketplace it manages, so
a file your `apply.sh` wrote by hand is yours to remove in `revert.sh`.
